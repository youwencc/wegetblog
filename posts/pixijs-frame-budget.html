把 60 帧塞进一台 2013 年的笔记本

2026.11.18 / 12 分钟 · 约 2,600 字 / 《像素数码工坊》

给《像素数码工坊》定最低配置的那天，我在纸上写了一行字：1280×720、60 帧、i5-3230M + HD 4000 核显。这不是市场调研的结果，是我家里正好有这么一台 2013 年的联想，而且我知道很多人的备用机就是这个水平。

定完这条线，后面所有「要不要加个后处理」「要不要上 2 倍素材」的讨论就都有了答案——不用讨论，跑不动。

先写死一个不体面的目标

目标机器：i5-3230M，4GB 内存，Intel HD Graphics 4000，Windows 10，Chrome。画布 1280×720，窗口化，不锁 devicePixelRatio。这套配置在今天大概是二手市场两百块的水平，但它能跑起来的游戏，在绝大多数人的设备上都不会有问题。

我把这条约束写在项目根目录的 BUDGET.md 里，每次想加功能就打开看一眼。文件里只有三行：

target: 1280x720 @ 60fps
device: i5-3230M / HD4000 / 4GB
frame: 16.67ms, 可用 13.3ms

第三条是后来加的。因为前两周我一直在拿 16.67 当预算，写什么都觉得还有余量，结果一到真实场景就掉帧。

一帧只有 16.67 毫秒，但能用的更少

60 帧意味着每帧 16.67ms，不过浏览器自己要合成、要跟 VSync 对齐，标签页切走再切回来还会有一次 GC。我按实测先划走两成，剩下 13.3ms，再分给四件事。

这张表最重要的一行不是最大的那个数，是最后那 3.47ms。它不属于任何人。谁想加功能，先从自己的份额里扣，不要动余量。这个规矩让「加一个小特效」这种请求变得具体：你要 1.5ms，那从哪儿挪？

测量方法很土：Chrome DevTools 的 Performance 面板录 30 秒，看 Main 线程的长任务；同时在 ticker 里打点，记录每帧的开始和结束。没用 stats.js，因为它自己的开销就有 1ms 上下，在我这个预算里太贵了。

把不动的图层烘成一张图

游戏里八成的像素是静止的：地板、墙、货架、贴在墙上的价目表。第一版我把它们全做成 Sprite 塞进 app.stage，draw call 直接到了 340。PixiJS 会合批，但前提是纹理和混合模式一致；我的图集切得太碎，顺序又乱，合不上。

改法很直接：进房间时把静态层渲染进一张 RenderTexture，之后每帧只画这一张。

// 进房间时烘一次，之后每帧只提交 1 个 sprite
const layer = RenderTexture.create({
  width: 1280, height: 720,
  resolution: 1, antialias: false,
});

const bake = new Container();
bake.addChild(floor, walls, shelves, poster);

app.renderer.render({ container: bake, target: layer });
bake.destroy({ children: true });

const room = new Sprite(layer);
app.stage.addChild(room);

代价是显存多占 1280×720×4，大约 3.5MB，换回来 290 个 draw call。这笔账在任何设备上都划算，包括我自己的台式机。

两个坑记一下：resolution 必须跟画布保持一致，别为了「更清晰」设成 2，那样等于每帧多采样四倍像素；烘完一定要 destroy 源容器，否则那些 Sprite 还挂在显示列表外面，纹理也不会释放。

粒子从 Sprite 换成 Points

修机器的时候会有火花、灰尘、蒸汽。第一版每个粒子一个 Sprite，峰值同时 800 个，帧时间直接多了 4ms。换成 ParticleContainer 之后好一点，但没解决根本问题——它只是降低了单次提交的成本，粒子数量还在那里。

真正有用的是回到更底层：一个 Points 对象，所有粒子共用一张纹理，位置、透明度、缩放写进顶点属性，一次提交完成。800 个粒子从 800 次提交变成 1 次。

// 800 个火花，共用一张 8x8 的贴图
const sparks = new Points(geometry, new TextureShader());
sparks.blendMode = 'add';

// 每帧只更新 attribute buffer，不重建对象
geometry.getBuffer('aVertexPosition').update();

限制也很明确：每个粒子不能单独换纹理，也不能有独立的旋转动画。我接受了，因为火花本来就不需要旋转，而蒸汽用不上叠加混合。

文本只重绘变化的那一行

经营游戏满屏都是数字：余额、时钟、客户耐心、零件价格。第一版用 Text，每帧 setText，哪怕值根本没变。Performance 面板里能看到一片密集的 canvas 重绘，每帧 2.2ms 就这么没了。

换成 BitmapText 好了不少，但还不够。最后加了一层脏标记：只有数值真的变了才 setText，而且只更新那一行，不重建整个面板。

function setStat(key: string, value: number) {
  if (cache[key] === value) return;   // 没变就什么都不做
  cache[key] = value;
  labels[key].text = format(value);
}

界面上的数字一秒最多变两次，而主循环一秒跑六十次。这个差距就是白烧的 CPU。

三个顺手做对的小决定

有些设置改一行代码就能省下 measurable 的开销，但要在初始化时定，后面改很麻烦：

  • antialias: false，roundPixels: true。像素游戏不需要抗锯齿，关掉省一次全屏混合；roundPixels 让精灵落在整数像素上，滚动时不会糊成一片。
  • resolution 固定为 1。高分屏上不追 devicePixelRatio，用 CSS 放大画布。像素反而更干净，填充率也回到了 2013 年的水平。
  • 页面隐藏就停 ticker。切到别的标签页还跑 60 帧，风扇会响，笔记本会烫。一个 visibilitychange 就够。
app.ticker.maxFPS = 60;

document.addEventListener('visibilitychange', () => {
  document.hidden ? app.stop() : app.start();
});
补充 maxFPS 只能限制上限，不能保证稳定。掉帧的时候先看 Main 线程，再看 GPU；这台 2013 的机器上，九成的问题在 CPU 侧。

结果，以及还欠着的账

在目标机器上跑了一个月，数字大概是这样的：

  • 1280×720 窗口，室内场景稳定 60 帧，复杂场景偶尔 57；
  • draw call 从 340 降到 47，其中静态层 1，角色 12，粒子 1，UI 33；
  • GPU 时间从 11.2ms 降到 6.4ms；
  • 主线程 JS 每帧从 6.8ms 降到 2.9ms；
  • 内存峰值 210MB，纹理占 96MB。

还没做完的：图集现在切成 12 张，理论上能合到 4 张，能再省一批 draw call；房间切换时的加载会硬卡 400ms，需要做分帧；存档序列化在主线程跑，大存档会掉帧。这些都进了 issue，不打算在 demo 之前动。

写完这篇我又回头看了一遍最初那张预算表，四个数字改了两个，结构没变。性能预算不是一堆优化技巧的合集，是你在写第一行代码之前决定的取舍。技巧可以后补，取舍补不了。
