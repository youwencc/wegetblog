给桌面小工具写一个 200 行状态机

2026.08.02 / 7 分钟 · 约 1,700 字 / TinyPlayer 重构

不是为了优雅。是因为三个月后我打开这段代码，发现自己已经看不懂了。

起因：一个 if 套了五层

TinyPlayer 的功能很少，但它有三个入口同时改同一份状态：托盘菜单、主窗口上的按钮、全局快捷键。用户按空格暂停，托盘图标要跟着变；用户点托盘切歌，窗口里的进度条要归零；播放失败时，三个入口都得知道现在是错误状态。

第一版我是这么写的：

if (player.IsPlaying) {
    if (isDragging) {
        if (e.Key == Key.Space) { ... }
    } else {
        if (deviceLost) { ... }
        else if (e.Key == Key.Space) { player.Pause(); tray.Icon = Pause; }
    }
}

你大概能猜到后面发生了什么：加一个「淡入淡出」的功能，改了六处；修一个「切歌时进度条闪一下」的 bug，引入了另一个 bug。问题不在代码丑，在于「现在是什么状态」和「这个事件该做什么」混在一起，每次都要人脑重新推一遍。

我想要的其实不是状态机

我想要的只有一件事：任何一个入口触发的事件，最终都走同一条路，改同一份状态，再由同一处去更新界面。状态机只是实现这件事最省事的形状。

所以设计目标只有三条：

  • 状态是有限的，能一眼数完；
  • 事件到状态的变化写在一张表里，不散落在各处；
  • 副作用（改图标、改窗口、写日志）集中在动作函数里，不写在判断里。

三张表：状态、事件、转移

状态四个：Idle（没歌）、Playing、Paused、Faulted（设备丢失或解码失败）。事件六个：Play、Pause、Next、Prev、Seek、DeviceLost。

转移表是一个字典，键是「当前状态 + 事件」，值是「下一个状态 + 该做什么」。没有列进去的组合就是忽略——这一点很重要，它让「按下暂停时按上一首」这种行为有了明确的答案，而不是碰运气。

代码

enum PlayerState { Idle, Playing, Paused, Faulted }
enum PlayerEvent { Play, Pause, Next, Prev, Seek, DeviceLost }

readonly record struct Transition(PlayerState Next, Action? Effect);

static readonly Dictionary<(PlayerState, PlayerEvent), Transition> Table = new()
{
    [(Idle,    PlayerEvent.Play)] = new(Playing,  () => StartPlayback()),
    [(Paused,  PlayerEvent.Play)] = new(Playing,  () => Resume()),
    [(Playing, PlayerEvent.Pause)] = new(Paused,  () => PausePlayback()),
    [(Playing, PlayerEvent.Next)] = new(Playing,  () => PlayNext()),
    [(Playing, PlayerEvent.Prev)] = new(Playing,  () => PlayPrev()),
    [(Paused,  PlayerEvent.Next)] = new(Playing,  () => PlayNext()),
    [(Paused,  PlayerEvent.Prev)] = new(Playing,  () => PlayPrev()),
    [(Playing, PlayerEvent.DeviceLost)] = new(Faulted, () => ShowFault()),
    [(Paused,  PlayerEvent.DeviceLost)] = new(Faulted, () => ShowFault()),
    [(Faulted, PlayerEvent.Play)] = new(Playing,  () => RetryDevice()),
};

public void Dispatch(PlayerEvent e)
{
    if (!Table.TryGetValue((_state, e), out var t)) return;

    _state = t.Next;
    t.Effect?.Invoke();
    StateChanged?.Invoke(_state);   // 界面只订阅这一个事件
}

四十来行，包含枚举和表。外面再包一层：所有入口（托盘、窗口按钮、热键）只负责把事件丢进一个队列，由 UI 线程按顺序取出来 Dispatch。

队列这一步很关键。全局热键的回调在别的线程，托盘图标的事件也可能来自 shell 线程，直接改状态迟早撞上。一个 ConcurrentQueue<PlayerEvent> 加 Dispatcher.BeginInvoke，问题就没了。

它不擅长的地方

诚实地说，这套东西有两个明确的短板：

状态一多就爆炸。四个状态六个事件是 24 个格子，还能手写。到十二个状态、三十个事件，表格会有 360 行，人就开始抄错。这时候该换成层次状态机，或者把播放器和界面拆成两个独立的状态机。

异步流程不好表达。比如「切歌要等解码完成」，这是一个跨越几秒的过程，不是一次瞬时的状态跳转。我的处理是加一个 Loading 状态，用回调推进；再复杂就该上 async/await 加一个取消令牌，别硬塞进转移表。

三个月后

重构完之后又加了两个功能：淡入淡出、播放列表循环模式。前者只加了一个状态和一个动作，后者只加了两个事件和四行表项。没有改动 Dispatch，也没有在任何一个 if 里翻找「现在到底是什么状态」。

代码总量没变短，甚至多了一点。但它变成了一张可以读的表：想知道「播放中拔掉耳机」会发生什么，去表里找一行就行。对我来说，这就是重构的全部意义。
